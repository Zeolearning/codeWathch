关键设计：闭包绑定 Context

每个工具函数通过工厂函数 make_xxx_tool(ctx: RepoContext) 创建，RepoContext 在构建时注入 repo_root，所有后续调用不需要再传路径——在用户的工作流视角里是透明的：

tools/read_file.py — 工厂模式
def make_read_file_tool(ctx: RepoContext):
    @tool
    def read_file(path: str, offset: int = 0, limit: int = 2000) -> str:
        resolved = ctx.in_repo_path(path)       # ← 自动限制在 repo 内
        lines = resolved.read_text().splitlines()
        return "".join(lines[offset:offset+limit])
    return read_file

1.5为什么需要 AST 解析？

java_symbols 和 java_index 是这个 agent 区别于 "grep + read_file 组合" 的核心价值。要理解它们为什么强大，需要先理解 tree-sitter 如何"看懂"Java 代码。

1.5.1 首先，tree-sitter 是什么？

tree-sitter 是一个增量解析器，它根据一个语言语法定义文件 （grammar.js）把源码解析成具体的语法树（CST，不是 AST）。 每一行代码、每一个字符在树里都有一个对应的节点。关键点：

  • 语法文件由语言作者编写，精确描述了该语言的 每一个语法规则
  • 解析结果是确定的——对同一段代码，100 次解析得到 完全相同的树
  • 注释、字符串字面量、空格在树中有自己的节点类型，不会和代码逻辑混淆

tree-sitter-java 的语法文件定义了大约 80+ 种节点类型，包括： class_declaration、method_declaration、field_declaration、 marker_annotation、annotation、block_comment、 line_comment、string_literal... 每种节点在树中有明确的 层次关系和字段名。

1.5.2 看看实际的树是什么样

用一段最简单的 Java 代码做演示。tree-sitter 解析后生成这样的树结构：

// 输入源码
@RestController
public class UserController {
    @GetMapping
    public List<User> getAllUsers() {}
}
# 解析后的树（简化）
program
└── class_declaration [name=UserController]
    ├── modifiers
    │  └── marker_annotation [name=RestController]
    ├── class
    ├── identifier [name=UserController]
    └── class_body [body]
        └── method_declaration [name=getAllUsers]
            ├── modifiers
            │  └── marker_annotation [name=GetMapping]
            ├── type_identifier [type=List<User>]
            ├── identifier [name=getAllUsers]
            └── block [body]

注意几个关键点：

  • marker_annotation 是 modifiers 的子节点——在语法层面， 注解是修饰符的一种，而不是"某行以 @ 开头的字符串"
  • class_declaration 和 method_declaration 各自有独立的 modifiers 子节点——注解和它修饰的目标在树中有明确的父子关系
  • block_comment、line_comment、string_literal 节点类型完全不同——注释里的 @GetMapping 永远是一个文本节点的一部分， 不会被解析成 marker_annotation

1.5.3 代码是怎么遍历这棵树的？

有了这棵树，要找到"所有的 @RestController 类"就变成了一个树遍历问题， 而不是"字符串搜索问题"。来看实际的遍历代码：

java_symbols.py — 树的遍历逻辑
# 第一步：解析源码 → 得到树
tree = PARSER.parse(source)
root = tree.root_node                              # program

# 第二步：遍历根节点的所有直接子节点
for child in _children(root):
    # 检查节点类型 —— 不是检查文本内容
    if child.type == "package_declaration":
        # 取 scoped_identifier 子节点，读出 "com.example.demo"
        pkg_node = _find_child(child, "scoped_identifier")
        result["package"] = _text(pkg_node, source)

    elif child.type == "class_declaration":
        # 进入 _parse_class → 递归遍历
        result["classes"].append(_parse_class(child, source))
java_symbols.py — _parse_class 解析单一类
def _parse_class(node, source):
    # node.type 一定是 class_declaration

    # child_by_field_name() 通过字段名定位 —— 不是通过搜索文本
    name_node  = node.child_by_field_name("name")        # → identifier
    super_node = node.child_by_field_name("superclass")   # → type_identifier (extends)
    iface_node = node.child_by_field_name("interfaces")   # → type_list (implements)
    body_node  = node.child_by_field_name("body")         # → class_body (花括号内)

    # 提取注解：找到 modifiers 子节点，在它的子节点中找 marker_annotation
    mods = _find_child(node, "modifiers")
    if mods:
        for m in _children(mods):
            if m.type == "marker_annotation":
                name = _find_child(m, "identifier")
                anns.append({"name": _text(name, source)})

    # 遍历 class_body 内部的子节点
    for child in _children(body_node):
        if child.type == "method_declaration":
            cls["methods"].append(_parse_method(child, source))
        elif child.type == "field_declaration":
            cls["fields"].append(_parse_field(child, source))

1.5.4 对比：grep 和 tree-sitter 在处理同一段代码时的区别

假设 Java 文件里有这段"迷惑性"代码：

// 情况 1：注释里的 @GetMapping —— 不是注解，是文本
/* @GetMapping("/old/api") */
public String oldEndpoint() { ... }

// 情况 2：字符串字面量里的 @GetMapping —— 不是注解，是字符串内容
String log = "received @GetMapping request";

// 情况 3：错误的注解名 @Getmapping（少写一个 p） —— 在 Java 语法里不合法
@Getmapping  // tree-sitter 解析的时候，这里会报错或者不产生 marker_annotation 节点
public void typo() {}

grep("@GetMapping")

✅ 命中真正的 @GetMapping（如果有的话）
❌ 命中注释里的文本（情况 1）
❌ 命中字符串里的文本（情况 2）
❌ 不会命中情况 3——因为它搜的是 @GetMapping，而拼写是 @Getmapping

结果：误报 2 条，漏报 0 条（但如果是反过来的情况就很难说了）

tree-sitter marker_annotation

✅ 命中真正的 @GetMapping（如果有的话）
❌ 忽略注释里的文本——block_comment 节点类型不是 marker_annotation
❌ 忽略字符串里的文本——string_literal 节点类型不是 marker_annotation
❌ 忽略拼写错误——@Getmapping 无法被解析为合法的 marker_annotation 节点

结果：零误报。只命中语法上确认为注解的节点。

grep 的匹配条件是 文本相等："字符串里是否包含 @GetMapping"。
tree-sitter 的匹配条件是 语法相等："这个节点的类型是 marker_annotation， 且它的 name 子节点的文本是 GetMapping"。
这就是"问语法结构"和"搜字符串"的本质区别。

1.5.5 为什么 grep 做不到的一些事，tree-sitter 能做到？

举三个实际场景：

场景 A："找出所有没有用 @Transactional 注解的 public 方法"
grep 能找出 "@Transactional"，但无法判断这个注解是属于这个方法、 还是属于整个类（类级别的 @Transactional 会作用于所有方法）。 tree-sitter 知道：method_declaration → modifiers → marker_annotation[name=Transactional] 是方法自己的注解；class_declaration → modifiers → marker_annotation[name=Transactional] 是类的注解。逻辑上可以精确区分。

场景 B："这个类继承了哪些类？实现了哪些接口？"
grep 可以搜 extends 和 implements，但如果一个类实现了 Serializable 但通过父类继承，grep 无法展开继承链。 tree-sitter 可以直接访问 class_declaration → superclass 和 class_declaration → interfaces 字段，而且可以递归爬父类文件。

场景 C："这个方法的参数类型和返回类型是什么？"
grep 得到的是模糊的文本片段，tree-sitter 通过 method_declaration → type 和 method_declaration → parameters → formal_parameter → type 精确提取类型信息。

1.5.6 两个工具的分工

工具 粒度 做了什么 类比
java_symbols 单文件 解析树 → 提取 package / imports / 每个类的 name / kind / annotations / fields / methods / extends / implements → JSON 给 LLM 看的"文件结构摘要"
java_index 全仓库 遍历所有 .java → 每个文件执行 _parse_file → 合并所有符号 → 写入 .code_watch/index.json → 支持按 kind/annotation/name 过滤查询 给 LLM 看的"仓库结构数据库"

总结：grep 解决的问题是"这个字符串出现在哪里"；tree-sitter 解决的问题是 "这段代码在语法上是什么"。 后者是理解代码结构的前提， 也是后续做 bug 分析（比如"找到所有没有 @Transactional 的 public 方法"）的数据基础。

系统提示词写在 agent.py 中，动态注入当前 repo 路径，指导模型遵循 opencode 风格的工作流：

# agent.py — _make_system_prompt() 生成的完整提示词

You are a Java code-reading assistant with access to a Java repository.
Repository root: {ctx.repo_root}

Core principles:
1. Explore before reading — use glob, grep, java_index first,
   then read_file on specific files.
2. Use java_symbols for structured Java AST info instead of raw file reads
   when possible.
3. Explain each step before acting.
4. Never claim you've read a file unless you actually called read_file or java_symbols.
5. Stay inside the repo root. Reject paths that escape it.
6. Prefer read-only bash commands (git, rg, find, mvn -q).

Tools available:
 read_file(path, offset?, limit?) — read file content
 glob(pattern, subpath?)           — find files by pattern

java_symbols（单文件 AST 解析）

为什么需要它？ 如果 LLM 只用 read_file 看 Java 源码，它读到的是 纯文本——必须自己"脑内编译"才能理解哪个类是哪个、注解在哪、 方法签名怎么拆。有了 java_symbols，直接把源码变成 结构化 JSON， LLM 一步拿到精确信息。

java_symbols(file)

无 AST — read_file("UserController.java") 返回纯文本：

// 38 行文本，LLM 自己提取"这个类叫 UserController"
// 它有两个注解 @RestController 和 @RequestMapping
// 有 4 个方法，每个有各自的注解...
@RestController
@RequestMapping("/api/users")
public class UserController {
...

有 AST — java_symbols("UserController.java") 返回 JSON：

{
"package": "com.example.demo",
"imports": ["java.util.List", "org.springframework.web.bind.annotation"],
"classes": [{
"name": "UserController",
"kind": "class",
"annotations": [
  {"name": "RestController"},
  {"name": "RequestMapping", "args": "(\"/api/users\")"}
],
"methods": [
  {"name": "getAllUsers", "return_type": "List<User>",
   "annotations": [{"name": "GetMapping"}],
   "parameters": [], "start_line": 19},
  {"name": "getUserById", "return_type": "User",
   "annotations": [{"name": "GetMapping", "args": "(\"/{id}\")"}],
   "parameters": [{"name": "id", "type": "Long"}]}
]
}]
}

LLM 一眼就知道："这是一个 @RestController，有 2 个 @GetMapping 端点， 一个接受 Long id 路径参数"。不需要自己解析花括号和注解位置。

🗂️

java_index（全仓库符号索引）

为什么需要它？ java_symbols 只能查一个文件。 java_index 预先解析 整个仓库的所有 *.java， 构建一个可搜索的索引。这样 LLM 问"仓库里有哪些 @RestController"时， 不需要逐个文件 grep + 手动理解——直接过滤索引即可。 甚至 LLM 都不知道具体有哪些注解，也能问。这就是后续做 bug 分析的数据基础。

java_index(kind?, annotation?, name_contains?, file_contains?)

无索引 — LLM 需要自己连招：glob("**/*.java") → 对每个文件 read_file → 在脑子里扫描 → 找到全是纯文本。 对一个 100 文件的仓库，这需要几十步。而且可能漏掉。
有索引 — 一步调用：

>> java_index(annotation="RestController")
{
  "stats": {"total": 39, "matched": 1},
  "entries": [{
    "kind": "class",
    "name": "UserController",
    "file": "src/main/java/com/example/demo/UserController.java",
    "annotations": ["RestController", "RequestMapping"],
    "methods": ["getAllUsers", "getUserById", "createUser", "deleteUser"]
  }]
}

total: 39 表示整个仓库索引了 39 个符号（类+接口+导入+方法）。 进一步过滤 kind="method" 可以只看方法。 这相当于给你的 Java 仓库建了一个"数据库表"。

4额外处理

在实现过程中遇到了几个坑，以下是解决方法和关键的技术决策：

  • 🧩 tree-sitter-java API 适配

    安装的 tree-sitter 是 0.26 版本，API 与 0.20 完全不同。
    问题：Language(tree_sitter_java.language(), "java") 报错；node.child_by_field_name("modifiers") 返回 None —— 因为 tree-sitter-java 语法中 modifiers 不是 named field， 而是匿名子节点。
    解决：改用迭代子节点 + type 匹配： Language(lib) 单参数构造； _find_child(node, "modifiers") 遍历 children 查找。最终写了 _find_child / _find_children 辅助函数，适配了 package_declaration、import_declaration、 class_declaration、method_declaration 等所有节点类型。

  • 📦 方法签名的「{」陷阱

    提取方法签名时，原始方案用 source.find(b"{")， 但 Spring 注解 @GetMapping("/{id}") 中含有花括号，导致签名被过早截断—— 变成 @GetMapping("/。
    解决：利用 tree-sitter 的 body field（block 节点）的 start_byte 作为分割点：source[node.start_byte:body.start_byte]， 精确得到完整签名。

    java_symbols.py — _make_signature
    body = _find_child(node, "block", "class_body")
if body:
    return source[node.start_byte:body.start_byte] \
                .decode().strip()
  • 🗃️ Java 索引缓存失效

    首次构建索引后，再次调用仍然返回旧数据（因为 _load_or_build 只要 index.json 存在就直接加载）。
    解决：在缓存的 meta 中记录所有 *.java 文件的 mtime 字典 file_mtimes。下次加载时比较 _get_java_mtimes() 是否一致，不一致则自动重建。

    java_index.py — 缓存校验
    cached_mtimes = data.get("meta", {}).get("file_mtimes", {})
current_mtimes = _get_java_mtimes(repo_root)
if cached_mtimes == current_mtimes:
    return data.get("entries", [])
# 否则自动重建
  • 🔒 bash 安全白名单

    开放 bash 工具必须防止恶意 / 误操作。定义了一个 _ALLOWED_COMMANDS 字典，每个命令对应一个子命令集合： None 表示所有子命令放行，set() 表示仅允许裸命令。 is_safe_command() 在所有 bash 调用前执行检查。

    bash_tool.py — 白名单结构
    _ALLOWED_COMMANDS = {
    "git": {"log", "diff", "show", "status",
             "branch", "rev-parse", "ls-files", "grep"},
    "rg":   None,      # 全部放行
    "find": None,
    "mvn":  {"help", "dependency", "validate"},
    "ls":   set(),    # 仅允许裸 ls（不限制 flags）
    "pwd":  set(),
}
  • 📐 semantic truncation + 环境隔离

    read_file 在截断处明确提示 --- truncated at line X of Y; use offset=X to continue ---， 让 LLM 能用 offset 继续读取——这一设计直接取自 opencode 的 Read 工具。 另外，系统 Python 环境存在 anaconda3 / system py3.10 混合问题导致导入失败， 通过 uv venv 创建独立虚拟环境彻底解决。
