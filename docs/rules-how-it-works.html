codeWatch · 规则生成与测试工作原理

从一个 Defects4J 缺陷的 BugAnalysis 出发,自动创造一条 Semgrep 规则,使其在 buggy 树命中、fixed 树静默。本文以 Lang-1 真实跑通的产物为例讲解,并贴出实际代码。

这不是 RuleRefiner 的精化流程。RuleRefiner 修一条已存在的 buggy 规则(跑 semgrep --matching-explanations 建谓词图 → 差分定位规则哪段判错)。codeWatch 是从零创造规则——没有规则可跑 explanation,所以只复用了 tree-sitter 解析 + graph.diff 的序列差分骨架,把语义从"规则执行路径的真值"重映射成"AST 节点在 buggy/fixed 的存在性"。

1 · 阶段 1:rule-gen-prep agent(语义选取相关方法)

为什么用 agent 而不是 diff?

开发者修复 diff(patch_src)只告诉你"机械改了哪些行",但哪些方法对 bug 才是相关的是语义判断——diff 会混入无关重构/空白改动。所以这一步交给一个 ReAct agent,以 root_cause + affected_files 为锚点,用现有只读工具探索两棵树,自主选出相关方法对。

单 RepoContext 覆盖两棵树的布局

checkout 把 buggy/fixed 放到公共父目录下,一个 RepoContext 即可让现有 7 个工具零改动地访问两棵树:

# rules/checkout.py
def checkout_both(project, bug_id, *, base_dir=None, refresh=False):
    # 布局:  tmp/rulegen-<project>-<bug>/
    #        ├── buggy/   <- checkout_defect(version="buggy")
    #        └── fixed/   <- checkout_defect(version="fixed")
    buggy_dir = Path(base_dir) / "buggy"
    fixed_dir = Path(base_dir) / "fixed"
    if refresh or not (buggy_dir / ".git").exists():
        checkout_defect(project, bug_id, version="buggy", workdir=str(buggy_dir))
    if refresh or not (fixed_dir / ".git").exists():
        checkout_defect(project, bug_id, version="fixed", workdir=str(fixed_dir))
    return Path(base_dir), buggy_dir, fixed_dir

agent 用 read_file("buggy/src/...") / read_file("fixed/src/...") 同时访问两棵树,路径 jail(ensure_inside)仍满足。两段式:ReAct 探索 → 结构化抽取 RelevantSnippets(镜像现有 analyze_bug 的做法)。

注意:agent 返回的是方法体片段(以 if 开头),不是完整方法声明。这对阶段 2 的解析是个坑(见下)。

2 · 阶段 2:AST 节点差分(核心细节)

这是从零创造规则的关键信号源:找出"buggy 中存在、fixed 中消除/改变"的结构节点,直接告诉 LLM"规则该匹配什么 / 该避开什么"。

2.1 tree-sitter 解析 + 两种 wrap 策略

复用 codeWatch 已有的 tree-sitter-java parser(tools/java_symbols.py 暴露的 PARSER)。但阶段 1 返回的片段不一定是完整方法声明,直接 class _Dummy { if(...) {...} } 会被 tree-sitter 误解析(if(x) 被当成构造器调用 → 假 constructor_declaration)。所以用两种 wrap 策略,取先成功的:

# rules/ast_diff.py
def _wrap_as_class(method_source):
    # 策略1:片段本身是完整 method_declaration
    return f"class _DiffDummy {{\n{method_source}\n}}\n"

def _wrap_as_body(method_source):
    # 策略2:片段是方法体/语句 → 包成 _m 的方法体
    return f"class _DiffDummy {{\nvoid _m() {{\n{method_source}\n}}\n}}\n"

def _parse_method_block(method_source):
    for wrapper in (_wrap_as_class, _wrap_as_body):
        source = wrapper(method_source).encode("utf-8")
        tree = PARSER.parse(source)
        for mtype in ("method_declaration", "constructor_declaration"):
            for node in _find_all_children(tree.root_node, mtype):
                body = _find_child(node, "block")
                if body is not None:
                    return body, source      # 返回方法体的 block 节点
    return None, None
Lang-1 的实际路径:片段以 if 开头 → 策略1 误解析成 constructor → 但策略2(void _m() { if(...) {...} })是合法 Java,找到 _m 的 block,成功返回。block 的直接命名子节点就是那条 if_statement。

2.2 语句序列抽取

取方法体 block 的直接命名子节点(跳过注释),每个节点算一个签名 (node.type, 规范化文本)。规范化 = 压平所有空白,让 foo( ) 和 foo() 视作相同。

def _statement_sequence(block, source):
    seq = []
    for i in range(block.child_count):
        child = block.child(i)
        if not child.is_named or child.type in ("line_comment", "block_comment"):
            continue
        seq.append((_signature(child, source), child))   # ((type, text), node)
    return seq

def _signature(node, source):
    return (node.type, " ".join(_text(node, source).split()))   # 规范化

为什么是语句级而非全树?Semgrep pattern 匹配的是语句/表达式粒度。更深子节点会和父语句的文本重复,反而嘈杂。语句级差分直接对口规则该匹配的语法单元。

2.3 difflib 序列对齐(改造 graph.diff 的骨架)

RuleRefiner 的 graph.diff(bad_path, good_path) 比的是同一规则图的两条执行路径(节点带"子 pattern 是否匹配"真值)。这里把它改造成两份独立的语句序列对齐,真值语义从"子 pattern 是否匹配"重映射为"节点在 buggy/fixed 是否存在"。用 stdlib difflib.SequenceMatcher 直接拿对齐结果:

sm = difflib.SequenceMatcher(a=buggy_sigs, b=fixed_sigs, autojunk=False)
for tag, i1, i2, j1, j2 in sm.get_opcodes():
    if tag == "equal": continue                              # 两边都有的语句 → 无差分
    if tag == "delete":                               # buggy 有、fixed 无
        for i in range(i1, i2):
            deltas.append(ASTNodeDelta(node_type=..., buggy_text=...,
                                       fixed_text=None, change="added_in_buggy"))
    if tag == "insert":                               # fixed 有、buggy 无
        for j in range(j1, j2):
            deltas.append(ASTNodeDelta(node_type=..., buggy_text=None,
                                       fixed_text=..., change="added_in_fixed"))
    if tag == "replace":                              # 同位置但文本不同
        deltas.append(ASTNodeDelta(..., change="changed",
                                   buggy_text=..., fixed_text=...))
difflib opcode含义映射成规则生成语义
equal两边签名相同(无 delta)规则无需关注
deletebuggy 有、fixed 无added_in_buggybug 模式,规则该匹配
insertfixed 有、buggy 无added_in_fixed修复引入(如 guard),规则该避开
replace同位置文本不同changed对照两版文本判断

教学小例子:yaml.load → yaml.safe_load

buggy:  Object o = yaml.load(s);      fixed:  Object o = yaml.safe_load(s);

block 的直接子节点都是一条 local_variable_declaration,签名因文本不同 → difflib 给一个 replace opcode → 一条 changed delta:buggy_text="Object o = yaml.load(s);" → fixed_text="Object o = yaml.safe_load(s);"。LLM 据此写 pattern: yaml.load(...) + pattern-not: yaml.safe_load(...)。

Lang-1 真实 delta(修复后)

buggy 和 fixed 的方法体在策略2 下各只有一条 if_statement 直接子节点(pfxLen 那个外层 if),签名因条件文本不同 → 一个 replace → 一条 changed:

{
  "node_type": "if_statement",
  "change": "changed",
  "buggy_text": "if (pfxLen > 0) { ... if (hexDigits > 16) {...} if (hexDigits > 8) {...} ... }",
  "fixed_text": "if (pfxLen > 0) { ... if (hexDigits > 16 || (hexDigits==16 && firstSigDigit>'7')) {...} ... }"
}
这条 delta 把"buggy 用裸 hexDigits > 16、fixed 加了 || (... && firstSigDigit>'7') guard"的核心对照连同两版完整文本喂给 LLM——正是规则该匹配 vs 该避开的关键。

2.4 与 RuleRefiner graph.diff 的关系

维度RuleRefiner graph.diffcodeWatch ast_diff
输入同一规则图的两条执行路径(节点带 match 真值)两份独立源码语句序列(节点带存在性)
前提已有一条规则可跑 --matching-explanations无需规则(创造场景)
对齐按 node_id 找交集 + 区间按签名(type+规范化文本)LCS 对齐
输出语义规则哪段子 pattern 在失败用例上判错哪个语句在 buggy 有/fixed 无(或反之)
复用面序列对齐 + 交集/区间检测的算法骨架;真值比较 → 存在性比较的语义重映射

3 · 阶段 3:规则生成(LLM)

3.1 prompt 组装

把阶段 1/2 的产物 + 规则 schema cheatsheet 喂给 LLM:

# rules/prompts.py
def build_generation_prompt(fix_delta, analysis):
    return f"""Bug: {analysis.bug_id}

Root cause:
{analysis.root_cause}

Affected locations (file:line — the rule SHOULD fire here on the buggy tree):
{affected}

### Method: {md.method.fqcn} :: {md.method.method_signature}
Buggy source: ```java ... ```
Fixed source: ```java ... ```
Structural delta:
- [BUG PATTERN — rule MUST match] if_statement: {d.buggy_text}     # added_in_buggy
- [FIX INTRODUCED — rule should NOT match] ... {d.fixed_text}      # added_in_fixed
- [CHANGED] ...                                                    # changed

Semgrep schema reference: {_SEMGREP_SCHEMA_CHEATSHEET}   # 句法模式 + 污点模式操作符表

Write ONE Semgrep YAML rule (Java) that matches the bug pattern and stays silent on the fixed version.
Emit the rule inside <FINAL_ANSWER>```yaml ... ```</FINAL_ANSWER>."""

输出契约沿用 RuleRefiner 的 <FINAL_ANSWER>```yaml ... ```</FINAL_ANSWER>,postprocess 用正则抽 fenced yaml 块。

3.2 Lang-1 实际生成的规则

rules:
- id: d4j-lang1-r1
  languages: [java]
  severity: ERROR
  message: "Hex number parsing missing overflow checks for leading zeros and type boundaries."
  patterns:
  - pattern-inside: |              # 锚定 hex 处理上下文
      if (pfxLen > 0) { ... final int $HEXDIGITS = ... - ...; ... }
  - pattern-either:                # 匹配 buggy 的裸分支(bug 模式)
    - pattern: if ($HEXDIGITS > 16) { return createBigInteger(...); }
    - pattern: if ($HEXDIGITS > 8)  { return createLong(...); }
  - pattern-not: |                 # 排除 fixed 的 guard(修复引入)
      if ($HEXDIGITS > 16 || ($HEXDIGITS == 16 && $FIRST > '7')) { ... }
  - pattern-not: |
      if ($HEXDIGITS > 8 || ($HEXDIGITS == 8 && $FIRST > '7')) { ... }

LLM 自述(metadata.explanation):

// deepseek-v4-flash 的推理
The bug is the missing overflow checks (`(hexDigits==16 && firstSigDigit>'7')` and
`(hexDigits==8 && firstSigDigit>'7')`) and the absence of leading zero stripping.
The rule matches the simplified `if (hexDigits > 16)` / `if (hexDigits > 8)` (buggy) and
uses `pattern-not` to exclude the fixed version where these have the additional `||` clauses.
This ensures the rule fires only on the buggy tree.

4 · 阶段 4:差分 oracle

4.1 为什么不走 semgrep test + marker?

RuleRefiner 靠测试文件里的 // ruleid: / // ok: 行标记算期望命中。Defects4J 测试文件没有这些标记。所以 codeWatch 直接 semgrep scan 两棵树,用 BugAnalysis.affected_files 的精确 file:line 作期望——消解了 marker 缺失问题。

4.2 oracle 与状态判定

# rules/evaluator.py
buggy_hits = scan_tree(rule.yaml, buggy_dir)   # semgrep scan --json --config rule buggy/
fixed_hits = scan_tree(rule.yaml, fixed_dir)   # semgrep scan --json --config rule fixed/

hit_expected = intersect(buggy_map, expected_map)     # 命中 ∩ 期望行
recall  = |hit_expected| / |all_expected|            # 期望行被命中的比例
precision = |hit_expected| / |reported|             # 命中中落在期望行的比例

if fixed_map:                 status = "FP"      # fixed 树有命中 → 规则没抓住修复点
elif not hit_expected:       status = "FN"      # buggy 上没命中期望行 → 漏检
else:                          status = "PASS"    # buggy 命中 ∧ fixed 静默

优先级:SYNTAX_ERROR > FP > FN > PASS。

6 · 复用与改造一览

来自 RuleRefiner怎么用
ts_cfg.TSHelper.gen_ast 思路复用 tree-sitter-java 解析(实际用 codeWatch 自己的 java_symbols.PARSER)
graph.diff 序列对齐骨架改造成 difflib 对两份语句序列做 LCS,真值→存在性

砍掉的理由

三段验证 syntax/regression/verify_fix简化为 scan buggy + scan fixed
semgrep_syntax.do_fix 语法自动修复可选后置,非核心
